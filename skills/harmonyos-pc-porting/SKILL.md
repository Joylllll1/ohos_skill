# HarmonyOS PC 移植与上架

把用户当前项目推进到其要求的阶段。先查清技术结构与现状，再给出该项目可执行的路线、完成授权范围内的工作，并留下可继续执行的记录。流程可复用，技术方案需要逐项目确定。

## 开始工作

1. 阅读项目说明、构建入口、适用的仓库指令、已有移植记录和当前 Git 状态。接手已有工程、检查进度或发现记录冲突时，先读 [接手与状态核对](references/resume.md)，识别当前开发、候选和已发布版本，再决定从哪里继续；不要重新初始化已有产物。当前任务已有授权继续有效，不从作为参考资料的旧记录推断新增外部操作授权。
2. 明确上游版本、必须保留的用户任务、目标 HarmonyOS 产品与版本/API、设备与 ABI、宿主开发环境、当前阶段和发布渠道。HarmonyOS 商业应用与 OpenHarmony 源码系统不是同一个目标。现有信息能确定的不要重复询问；影响路线或发布主体的未知项集中询问，其余先标待确认。
3. 可运行 `python3 <skill目录>/scripts/porting_helper.py inventory <项目目录>` 快速定位清单和构建文件，再按需阅读。结果只是文件线索，跳过目录、扫描上限和未解析的依赖必须保留在结论中。它默认跳过 `output/`、`build/` 等目录，不能用于判定没有发布包或验证记录；沿已有记录定向检查这些位置。
4. 新项目用 [计划模板](assets/porting-plan.md) 建立一份项目工作记录；已有项目沿用原来的记录位置，补缺项即可。需要机器可检查的阶段台账时，运行 `python3 <skill目录>/scripts/porting_helper.py init <新记录.json>`。不要为了套模板重排已有工程。
5. 按用户请求记录本轮终点：评估、原型、本地可安装、上架候选包、已提交、审核通过或实际上线。“准备上架”以候选交付为终点；“上架发布”还要跟进发布状态。“到哪一步”不明确且影响外部动作时先完成可做部分再澄清。
6. 建立能执行的环境基线：核对实际源码/工作副本、宿主 OS/架构、可用 SDK/DevEco/编译工具、依赖获取入口、磁盘与目标模拟器或设备。不把本机 Node/Python 版本、已有 SDK 或可下载镜像当成默认值；按该项目要求查证。先确认 agent 可用的文件/终端/联网/设备或浏览器工具。缺 SDK、镜像、账号或工具时按 [交接与恢复](references/handoffs.md) 处理，技术步骤仍尽可能自动完成。

## 根据项目选择路线

阅读 [技术路线](references/routes.md) 中相关部分，形成“原有能力 → 可复用部分 → 平台边界 → 候选实现 → 最小验证 → 失败后的备选”。语言名称或一个依赖文件不足以决定路线。

- Web/Electron：区分渲染层、桌面主进程 API、Node 原生模块、后台进程。先验证 Web 宿主与关键桥接。
- C/C++ 与 GTK/Qt 等 GUI：分开验证计算核心、工具包后端、窗口/输入和依赖 ABI，不能从 C/C++ 支持推断 GUI 工具包已可用。
- Python 等解释器：分别评估运行时、原生扩展、进程模型和资源分发；复用界面与重建界面是独立决策。
- Java/.NET/Rust/其他框架或混合架构：先寻找目标版本支持依据与最小原型，无法确认时保留为待验证方案。不要预设某一种宿主或运行时组合。

按需读取 [官方来源索引](references/sources.md)。候选路线不构成当前 SDK 的支持承诺。修改公开 API、打包方式或上架规则前，核对当前目标版本的官方文档；记录访问日期、适用版本及无法读取的部分。

## 分阶段推进

| 阶段 / 台账 ID | 本阶段要得到什么 | 能够进入下一阶段的证据 |
|---|---|---|
| 范围与盘点 `scope` | 功能边界、技术画像、依赖与平台能力表、发布渠道 | 上游和目标明确，关键未知项有验证安排；删除或替代功能得到用户认可 |
| 路线原型 `route_proof` | 优先验证最不确定的平台能力 | 最小链路实际运行；记录环境、ABI、失败条件及备选路线，不只给静态设计 |
| 构建与打包 `build` | 可复现的依赖获取、补丁、交叉构建和包组装 | 构建命令/版本/日志、目标 ABI 与实际包内容核对；宿主编译不等于目标构建 |
| 功能适配与集成 `integration` | 对齐用户任务；桥接、资源、存储、生命周期接通 | 功能矩阵逐项结果、错误路径回归、未支持能力明确标出 |
| 目标环境验证 `device_validation` | 项目约定范围内的桌面体验与核心任务验证 | 可采用匹配系统/API/ABI 的模拟器、本地或云真机；写明环境与覆盖范围，不用构建结果替代 |
| 发布候选与材料 `release_candidate` | 按渠道准备候选：本地分发的可安装包与操作说明，或商店包与材料 | 对应候选包哈希、适用签名验证及交付检查；阅读 [发布流程](references/release.md) |
| 提交审核 `submission` | 候选版本已实际提交审核，可追踪 | 平台“已提交审核”回执或状态；仅上传成功不能标 pass，未提交保留 pending |
| 审核、发布与维护 `review` | 当前候选审核结论、发布检查点与整改跟进 | review/pass 仅表示该候选审核通过；退回保持 blocked/pending。若目标为上线，还须核对该版本实际发布，见 [发布检查点](references/release.md#发布检查点与完成条件) |

阶段可以迭代、部分工作可并行；从当前阶段接续，不要求已有工程从头再做。原型发现根本障碍时回到路线决策。发布材料可以提前准备，功能、隐私和截图要随候选包更新。每次改动使哪些旧证据失效，需要一并标注。

台账八阶段是检查索引，不是严格串行调度器，也不自动判定整项任务完成。`next_gate` 只是台账顺序上第一个 pending/blocked 阶段，不是执行指令；接手时可能代表证据待补而非动作未做，先按 [状态核对](references/resume.md) 决定下一动作。收尾根据用户要求的终点与实际发布检查点判定，不能因为八个状态均 pass 就把“审核通过”写成“已上线”。

用户只要评估时，交付路线与验证计划；要求实施时，继续执行已授权的代码与验证工作。没有真机时可使用匹配的模拟器推进原型、功能集成与目标环境验证；不把“拥有真机”作为启动或阶段完成的固定前提。根据实际硬件依赖、已知设备特有问题、用户目标和渠道要求判断是否需要补本地/云真机测试，并保留具体未测项。连可用模拟器也没有时，完成本机可做部分并交接运行验证，不能用构建成功替代运行结果。只做本地分发时，说明渠道后可将 `submission` / `review` 标为不适用。

## 问题处理与验证

### 需要用户处理时：交接、等待、核验、继续

需要登录、设备/账号授权、补充材料、用户决定或平台处理结果时，读取并执行 [交接与恢复](references/handoffs.md)。保存明确的记录路径，按阻塞项分别追踪“谁处理、做什么、如何核验、恢复哪一步”。暂停依赖项，继续独立工作。用户完成后先核验，再恢复；建应用、上传、提交、发布等外部动作结果未知时，先查询已有结果，不能直接重试。

普通编译报错或能从项目查到的信息继续自行处理。等待超时不是用户完成；登录完成不是新增发布授权。宿主不支持持续等待时，明确交接并在用户回复后续接，不承诺后台常驻或自动唤醒。

遇到问题先定位发生层：宿主工具链 / 目标依赖与 ABI / 系统能力 / UI 与输入 / 资源与沙箱 / 签名与安装 / 发布渠道。保存最小复现和错误原文，查对应版本文档，一次验证一个假设。项目专属补丁只在适用条件已证实时使用。

按 [验证指南](references/validation.md) 建立功能与设备矩阵。记录通过、失败、未测和有意不支持；保留原有功能与替代功能的差别。Mock 桥接、降级界面、被禁用模块和主机测试要明确标注。

台账检查：

```bash
python3 <skill目录>/scripts/porting_helper.py check <阶段记录.json> --root <证据根目录>
```

该命令仅检查台账结构、文件及哈希完整性和证据环境标签。退出码 0 可包含未完成阶段，不能据此声称应用可用、规则合规或审核通过。证据内容和覆盖范围仍由 agent 与开发者核验。

## 发布与交付

上架时读取 [上架流程](references/release.md)，逐项核对所选渠道。通用商店要求、社区协作约定、课程交付要求分别标注，不能相互冒充。开发签名、Release 构建、发布签名、上传成功、审核通过、实际上线分别记录。

可准备代码、候选产物、材料草稿及具体提交清单。账号登录、资质确认和发布主体的声明由拥有相应权限的人完成；上传、提交审核、正式发布等外部操作须在当前任务授权范围内。不要因用户只说“准备上架”就推断其要求立即发布。签名密钥、密码和令牌不写入台账、日志摘要或技能资源。

每次交付至少说明：当前阶段；本轮实际改动；验证对象与环境；未解决事项；下一步命令或操作及所需输入。流程文档应让下一个人可以接着做，而不是只有一份“已完成”清单。
