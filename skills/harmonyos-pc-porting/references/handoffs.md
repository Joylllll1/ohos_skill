# 用户接手、外部等待与断点恢复

在实际缺少条件时使用本指南，不在任务开始时要求用户一次完成所有账号操作。先自行检查可观察信息；已具备的条件不重复要求用户操作。

## 各环节如何交接

| 环节 / 谁处理 | 用户可能要做什么 | agent 如何确认并继续 |
|---|---|---|
| 源码与依赖访问 / 用户或仓库管理员 | 登录源码服务、授予仓库权限、配置私有源或提供合法可访问的副本 | 用当前构建所需入口验证可读，记录实际 revision；网页登录不自动代表 Git/包管理器已认证 |
| 个人代码托管 / 用户或 agent | 仅需要托管且缺仓库时，在已确认的 GitCode 个人账号建仓，返回 HTTPS/SSH clone 地址 | 先查已有远端，复用对应仓库或 fork；核对返回地址的归属和分支后按授权 push；本地移植不以建仓为前置 |
| 社区申请与 PR / 用户、社区管理员或维护者 | 用户授权或提交建仓 issue；管理员回复社区仓库地址；贡献者再提 PR，维护者审查合并 | 按 [社区交付步骤](release.md#5-可选的社区交付分支) 查重，记录个人仓库、issue、社区仓库/PR 链接及下一处理者；未提交草稿不记为等待管理员，已有申请不重提 |
| 工具与 SDK / 用户或 agent | 安装需要的 DevEco/SDK/镜像，接受许可、系统授权或提供安装位置 | 检查真实版本、路径与可执行性，重新查询镜像/设备；下载完成不等于安装成功。可自动执行且已授权的普通安装配置由 agent 完成 |
| 路线与功能范围 / 用户 | 决定重写 UI、替代依赖、取消功能或调整目标设备 | 解释可选方案的实际影响，记录选择；不把“继续”解释为接受未说明的功能删减 |
| 账号、身份与权限 / 用户或管理员 | 在需要登录的那个应用完成登录/扫码/验证码；实名认证或取得发布角色 | 核对当前工具、账号主体及目标应用可见性和操作权限；登录不代表已获应用权限 |
| 应用与发布身份 / 用户或 agent | 按授权创建/关联项目和应用，确认名称、包名、APP ID、设备和地区 | 读取已有记录防重复创建，保存非敏感标识；账号或应用不匹配时先澄清 |
| 签名 / 发布者或 agent | 在本机安全配置证书/Profile/密钥库，必要时由用户输入密码或完成云签名交互 | 验证实际配置/包内签名与目标应用匹配；不得要求把密码、验证码、私钥发到聊天或报告 |
| 运行环境 / 用户或 agent | 启动模拟器；或连接设备、解锁、接受调试授权 | 查看设备列表及系统/API/ABI，显式选择目标。多台设备不猜；新设备/会话先查当前状态，避免装错 |
| 运行测试 / 用户或 agent | 执行无法自动化的物理操作或检查，提供步骤与观察结果 | 使用对应候选包版本核对日志/截图；用户确认与工具独立验证分别记录，不把未观察场景写为通过 |
| 发布材料 / 发布主体 | 确认联系信息、真实数据行为、授权/资质或备案情况，补充必要文件 | 核对所选渠道的具体字段与缺项；只请求当前缺少且影响提交的材料 |
| 上传/审核/发布 / 平台、用户或 agent | 若需要，完成平台交互、选择发布时间或解决平台返回的问题 | 先确认准确的账号、应用、候选版本和已有请求状态，再决定等待、整改或执行下一操作 |

## 发出请求之前

把任务分为 agent 可解决的错误、用户操作、用户决定和外部平台等待。不要把正常的上传检测或审核处理中误报为需要重新登录。对于有用户接管/提问工具的宿主，按工具约定发出请求；普通聊天中用清楚的操作说明完成交接。

每次请求应有：受阻步骤、观察到的原因、具体操作位置、完成标志、恢复检查方法和交接记录的可点击路径。例如：

> 签名构建停在 DevEco 登录。请在当前 DevEco 的华为账号窗口完成登录，看到已登录后回复“DevEco 登录好了”。我已把进度保存在 `<项目>/docs/porting-plan.md` 的 H1。收到回复后检查该工程的签名条件，再继续构建；等待期间先整理本地依赖许可清单。

这里的路径只是示例，实际请求必须替换成真实记录路径。若当前任务只读、不允许写文件，则把同样的断点信息完整交付在回复中，不能声称已落盘。

## 持久记录多个阻塞项

沿用现有计划；没有时在项目建立一份明确入口，如 `docs/porting-plan.md`，使用 [模板](../assets/porting-plan.md)。每个未完成条件用 H1/H2 等独立标识，记录：

- 哪一步依赖它、由用户/管理员/平台处理、当前状态和最后检查时间。
- 应用/工程位置、目标账号的非敏感标识、设备或候选版本；候选产物路径与哈希。
- 要求的操作、可观察完成标志、验证方法、核验结果。
- 已完成的工作、可独立继续的工作、满足条件后下一动作。
- 当前任务授权来源与边界；外部动作已执行到哪一步、是否确认生效。

JSON 台账的 `blocked` 与非空 `reason` 只做阶段摘要，指向具体交接记录。一个条件完成，只解决对应条目；同一阶段尚有其他必要条件未完成时仍保持 blocked。解决后改 pending 并继续验收，不能直接改 pass。阶段 blocked 不是让所有其他任务停下的全局锁。

阻塞必须关联当前范围内的具体操作。例如用户只要求交付商店候选包与材料（本轮不提交），而签名方式和材料准备不依赖商店发布角色时，“发布角色待开通”只是未来提交的前置事项，不能阻塞当前候选交付；如果当前所选签名或应用配置确实需要该权限，再阻塞相应步骤。

## 等待与恢复

1. 暂停依赖未满足条件的动作，继续独立任务。不要忙轮询，也不要重复运行已知必失败的命令。等待输入/接管工具超时不代表用户完成或授权。
2. 用户回复后按标识核对已完成哪个条件。含糊的“好了”且存在多个不同前置条件时，先观察可验证状态，再仅澄清仍有歧义的部分。
3. 重新确认工程目录、账号、目标设备、有效签名配置和候选版本。浏览器、DevEco、Git、CLI 的登录态不可互相推断。终端环境变量和进程也可能在中断后失效，应重建所需环境，不记录访问令牌。
4. 用户做完但验证仍失败时，说明具体差异并请求最小补充动作。无法独立观察时记录“用户确认、未独立核验”，用合适的非破坏性操作验证，不伪称成功。
5. 本地构建/检查重试前核对它是否仍在运行或已产出结果；不要重复启动同一长构建。外部操作采用下一节的结果核对规则。
6. 更新恢复记录，仅重做受影响的步骤。候选包或源码发生变化时，保留旧版本历史，将受影响测试/材料/候选状态退回 pending，标明为何失效；新版本不能继承旧版本的已提交或已审核状态。

如果宿主支持当前任务内等待或观察，可以使用其机制；只具备逐轮聊天时，交付断点并告诉用户完成后回复。不要保证会话结束后继续监听、自动察觉登录或自动唤醒，也不要为一次审核临时创建定时自动化来冒充等待。

换会话时提供这样的续接语句，并替换成实际路径：

> 使用 $harmonyos-pc-porting 继续 `<项目绝对路径>`，先读取 `<交接记录绝对路径>`。H1 的 SDK 已安装，H2 的发布角色仍待管理员处理。继续完成可执行的构建和上架准备，暂不提交。

新会话先读取记录并按 [接手与状态核对](resume.md) 核验现场，保留有效产物；用户在会话外完成的后续操作可能已经改变阶段，不直接照旧断点重做。记录中的授权说明用于定位历史；以当前用户指令或可核实的持续任务授权为准。若本次外部提交范围不清楚，只暂停那项外部动作，仍可继续已明确的准备工作。

## 外部操作结果未知时，先核对结果

创建项目/应用、上传、提交审核、发布，或建仓、提交 issue/PR 后遇到超时、断线或用户接管，先记录“结果未知”。不要直接照抄“重试上一操作”。

代码托管或社区操作先核对账号、目标仓库、已有 issue/PR、提交时间及关联项目/上游；查询已有结果后再决定接续。个人 push 成功不能解锁未经授权的公开 issue/PR 提交。

读取同一账号/应用下的实际状态，核对 APP ID、bundleName、versionCode、候选哈希或平台包标识、尝试时间及回执。平台未提供哈希时保留本地上传文件哈希与平台包 ID 的对应，不假装有远端哈希校验。

- **已成功或仍处理中**：接续该条记录/请求，不重复创建、上传或提交。
- **明确失败或未发起**：根据错误修复后，在已有授权和确认的候选范围内重试。
- **仍无法确认**：保持未知并等待/请求用户核对状态；不要通过再次点击来“试一下”。

若用户在接管时已完成提交，记录真实平台结果，不再提交一次。若等待中本地生成了新包，旧候选和新候选分别追踪；不能因用户说“继续”就把针对旧版本的授权与验收转移到新包。

## 等待平台检测、审核和定时发布

记录回执、当前状态、候选身份、下一查询位置/方法、最近查询时间和下次需要的条件。普通任务中查看当前状态并交接；用户明确要求在当前任务跟进时，在宿主可持续执行的范围内作有间隔的检查，只有状态变化或需要用户操作时更新。不要承诺审核时长或后台无限等待。

pending 标记的是仍在处理的阶段：上传校验中且未提交时 submission/pending；官方显示对应候选已进入审核时 submission/pass、review/pending，不能因为审核未结束把已完成的提交改回 pending。说明当前等待的是平台结果，不要求用户反复“重新提交”。平台明确要求补资料或修复时，将受影响阶段标 blocked 并列具体项；退回后保留原提交回执，读取报告，回到对应代码/材料和回归步骤，准备下一次提交的状态。通过后按用户终点判断完成或继续 [发布检查点](release.md#发布检查点与完成条件)。定时发布尚未生效时仍是 scheduled，不能写为已上线。
