# 从候选包到上架与审核整改

先核对 [来源索引](sources.md) 中当前目标渠道的发布、签名、支持设备和素材规则。字段、大小、尺寸、SDK 要求和控制台入口可能变化；采用当前文档/控制台显示值并记录日期，不把单一项目的素材数量或 SDK 版本设成通用常量。

接手已有发布进度时，先按 [状态核对](resume.md) 对齐版本与最新结果，再选用本页适用步骤。用户明确确认已上架但尚无独立平台证据时，检查/规划结论注明来源并转入收尾；不把下面的新候选提交步骤重新全跑一遍。实际执行外部动作前仍按对应版本的当前平台状态核对。

## 1. 提前确定身份和渠道

确认是自用安装、华为应用市场分发，还是额外参与 OpenHarmonyPCDeveloper 社区/课程交付。记录发布主体、应用标识、设备范围及地区；账号实名认证、资质、行业材料、APP 备案的适用性按对应渠道实际要求确认。资质责任不从社区仓库所属组织推断。备案/资质等前置条件提前安排，不等最终包完成后才发现阻塞。

在当前开发者控制台确认项目、应用与账号的归属及权限。所选流程需要 AGC 项目时先复用或创建项目，再创建/关联 HarmonyOS 应用并取得 APP ID；已有应用不重复创建。随后核对包名、支持设备与目标分发渠道，记录非敏感标识。

应用名称、包名、仓库名不同：显示名称调整不代表应更换已注册 bundleName。注册前检查规则和可用性，已注册后先核对平台限制及升级/数据影响。公开搜索找不到重名不能证明商标权或商店名称可用，遇到授权审核按具体反馈准备材料。

**仅本地分发**：`release_candidate` 指与所选设备和签名条件兼容的安装包、哈希、安装/更新/收集日志步骤及已测范围。按所用工具核对调试签名设备限制或其他适用方式；不用准备商店 APP、商店发布签名或上架截图。`submission` 和 `review` 可标 not_applicable，注明“仅本地分发”。下面商店专属材料和审核步骤仅在选择商店渠道时执行。

## 2. 整理发布候选

- 明确实际构建工作副本、源码/补丁版本和最终随包依赖，清除影响本次产物的旧缓存需要依据，避免盲目删除工程。
- 区分可安装 HAP 与提交用应用包；按当前渠道核对实际需要的发布格式。华为文档的标准 HarmonyOS 发布流程使用发布 APP，不能只交付调试 HAP 就宣布完成上架准备。
- 对准 bundleName、版本、支持设备及 SDK 要求；编译使用 release 模式不等于具备发布签名。
- 签名按当前 DevEco/AGC 支持的流程办理。核对证书、Profile、密钥库的用途、对应关系及实际文件路径；调试和发布配置分开，使用可用的官方验签工具保存结果。
- 证书文件可能包含链；不要只解析第一张证书就判定整套材料不匹配。区分文件路径、签名链与 Profile 匹配、以及最终产物实际用了哪套配置，避免无依据地要求重新生成密钥。
- 不将私钥、密钥库、密码、令牌或带敏感值的完整配置复制到报告、技能包或公开仓库。流程记录只保留非敏感标识和验证结论。
- 核对发布 APP 包含的业务载荷与已测试 HAP 的对应关系，并保留哈希。未能验证对应关系时，作为待办。

## 3. 准备与代码一致的材料

| 材料 | 核对内容 |
|---|---|
| 名称与图标 | 控制台、系统应用列表、窗口/任务标题、页面标题、介绍和截图一致；改名后重建、安装检查 |
| 功能介绍 | 只声明实际可用能力；明确不能使用的驱动、模块、云功能或语料，不把 mock 或降级写成完整支持 |
| 截图 | 对应真实候选版本的真实 UI，标明采集设备/模拟器；不把设计预览当产品运行证据，按当前渠道尺寸和内容要求处理 |
| 隐私与权限 | 从实际权限、存储路径、数据流、外部图片/API/统计/第三方 SDK 核对；按控制台填写 PC 隐私标签及敏感/受限权限的用途和证明材料；本地计算不自动等于完全不联网 |
| 开源与授权 | 上游、实际分发依赖、版本、来源、许可和许可原文；按许可及渠道核实相应义务，不把开源许可当成名称/商标授权 |
| 操作与测试说明 | 核心流程、登录/测试条件、设备要求、已知限制、联系与支持方式；测试账号单独安全交付 |

素材制作和审核合规是两项工作。当前 skill 负责清点、指导、核对和在可用工具下准备材料；没有图像/浏览器工具时明确交接，不伪称已生成、已截图或已上传。

隐私声明的“记录名称”和实际声明正文可能不同；发现名称不一致需核对正文、托管页面、绑定记录及缓存状态，不能只凭下拉框猜测根因。

## 4. 上传、提交与审核

在用户授权的范围内辅助控制台操作。没有授权外部提交时，先交付可审阅的包、材料、操作步骤和剩余账号事项；用户已明确授权则不要反复索要同一许可。

操作前固定本次候选身份：源码及未提交改动、包路径与 SHA-256、bundleName、APP ID、versionCode、材料修订，以及此次提交尝试的标识/时间。平台检测、登录或审核需要等待时读取 [交接与恢复](handoffs.md)。上传/提交/发布超时或用户接手后，先查询相同候选和尝试的已有结果；已成功或处理中就沿用，结果未知时不盲目重复操作。

逐项记录：

1. 上传了哪个包（哈希/版本）以及平台校验结果。
2. 绑定哪些设备范围、地区、隐私声明和素材，是否还有待填写字段。
3. 是否真正提交审核，以及回执/时间/状态。
4. 审核通过、退回或待处理，不能把“上传成功”写成“已上架”。
5. 如审核通过后仍需选择发布时间或发布操作，记录实际执行情况，再确认上线状态。

软件包检测和审核仍在处理中时，保存平台回执与下一查询入口，按宿主能力和用户要求等待或交接，不能宣称正在后台长期跟踪。出现补资料请求再询问缺少的具体材料。材料被退回但二进制未变时，可按平台允许的流程修订材料后重新提交，保留旧尝试记录，不强制重建或提高版本号；是否需要新包/版本以具体反馈和当前平台要求为准。

审核退回后建立“反馈 → 核实/复现 → 代码或材料修正 → 受影响范围回归 → 候选与材料更新 → 重新提交”记录。代码或打包内容改变时出新包；纯材料修正按平台允许方式复用原包，更新材料修订及提交尝试。验证不足时给出具体未测环境，例如“较低系统版本模拟器通过，审核所用较高系统版本设备尚未完成交互回归”。

已知审核路径尚未验证时，不推荐将候选写为“已验证可重新提交”；继续完成其余材料并安排相关条件的回归。该判断来自当前已知缺陷的验证风险，不是凭空增加一条官方强制设备规则。如果用户明确选择在验证不足时提交，说明未测范围并核对渠道是否允许，按其授权办理，不能补写通过结果。`review` 的 pass 只代表当前候选的官方审核通过；退回时保留反馈证据及 pending/blocked 状态。

### 发布检查点与完成条件

本轮终点在项目计划中确定，不由 helper 的 `next_gate` 自动推断：

| 用户要求的终点 | 应交付/观察到的结果 |
|---|---|
| 评估、原型、本地安装或上架候选准备 | 对应方案、原型证据、安装交付或候选包与材料；未请求的外部提交不执行，未执行阶段保留 pending 或按渠道标不适用 |
| 提交审核 | 当前候选实际已提交的回执；明确仍在审核，不能称已通过 |
| 跟进审核通过 | 该候选的官方通过状态；退回则按用户范围整改并继续，不把旧版本通过结果带给新版本 |
| 上架发布 | 处理自动/手动/定时发布分支，确认所请求版本、设备和地区的实际发布状态 |

通过审核后，读取平台实际发布方式。自动发布时观察最终状态；手动发布时在当前授权范围内执行，没有明确发布授权则对准备好的具体版本请求确认；定时发布时记录时间和时区，未到时仍记 scheduled，按等待机制接续。若发布开关失败或响应未知，按已有尝试查询结果，不能只看到按钮被点击就记成功。

在计划中单独保存 `发布状态`（例如未提交/审核中/退回/审核通过待发布/定时发布/已发布/未知）、对应版本、地区/设备、证据、最后查询和下一动作。`review=pass` 和 `next_gate=null` 均不自动代表该检查点完成。

平台显示已发布后，在可用的目标设备/地区核对商店可见的应用身份与版本，并在可行时确认安装启动或更新结果。若只能看到平台已发布状态，明确报告“平台已发布；商店可见性/安装未复核”，保留待核验项，不能声称完整分发验证通过。第三方镜像、旧版本搜索结果或其他地区页面不能替代当前候选的证据。

完成判据按已约定终点执行：仅要求完成平台发布时，确认平台已发布可交付该结果，并单列分发抽查未测项；明确要求商店可见或安装验收时，该项未确认就仍有待办。不要把无法抽查安装误写成“平台未发布”，也不要擅自扩充用户的完成条件。

## 5. 可选的社区交付分支

仅用户选择 OpenHarmonyPCDeveloper 社区渠道时，核对其当前建仓、命名、贡献、版本和发布规范。`ohos_项目名`、特定 `based on/from` 命名及社区仓库地址属于该渠道语境，不能当成所有 HarmonyOS 应用的商店规定。

该分支可能包含建仓申请、源代码与补丁、构建说明、README、License、ChangeLog、第三方清单和 PR。当前社区《贡献指导》明确要求适配项目在根目录提供 `README.OpenSource`；适用时按该指南记录字段，不能将其外推为所有 HarmonyOS 应用的要求。公开仓库合并与商店审核分别跟踪。

## 6. 上线后维护

保存发布版本对应的基线、构建记录、依赖锁定、测试矩阵和材料。后续 SDK/依赖升级或新增权限时，复查受影响的路线与材料；修复发布按渠道更新版本、重测和提交。上架技能交付不等于承诺持续监控。
