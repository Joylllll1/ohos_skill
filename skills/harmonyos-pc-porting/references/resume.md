# 接手已有项目与状态核对

用于“做到哪了”“继续移植/上架”、跨会话接手，或旧计划与最新信息冲突的场景。先得到可信的当前快照，再选择需要推进的工作，不要求已有项目重新通过一遍全部阶段。

## 先找对版本和记录

1. 从现有 README、计划和交接入口，定向找最近的构建、回归、审核与发布记录；结合用户指定的会话获取线索。历史助手的结论不能代替底层产物或回执；无法访问会话时说明实际检查范围，继续查本地记录。
2. 区分当前工作副本（路径、分支、提交、未提交修改）、待发布候选、已发布版本。按包名/APP ID、版本号、包哈希或平台包标识关联；同名文件、相同 versionName 或最新 HEAD 均不足以证明是同一候选。源码与包的对应依赖构建来源记录，不从文件名猜测。
3. 沿记录检查产物和证据是否仍存在，必要时重算哈希、读取包元数据。`inventory` 和普通文件搜索可能跳过产物目录或忽略文件；未跟踪、被忽略不等于无价值。不要为接手而清理输出、切换分支或覆盖工作区。
4. 判断任务需要的环境能否恢复：原工程是否在临时目录或其他 worktree，所需 SDK、原生构建宿主、依赖入口和锁定记录是否对应这次产物。工具文件存在不等于完整构建可复现。远端分支仅在检查范围需要时只读查询；未查询的缓存引用标为本地记录。

## 对冲突逐条判断，不设简单的来源排名

在现有计划中记录：**具体事实、所属版本/环境、事件时间、记录或本次核对时间、来源、独立核验情况、采用结论、仍待核对事项**。事件时间未知就留空；今天听到“已上架”不表示今天上架。

| 现场情况 | 处理方式 |
|---|---|
| 旧记录写“待提交”，用户明确确认同一版本后来已正式上架 | 当前快照写“已发布（用户确认，尚未独立核验）”，按收尾安排计划；旧记录保留为历史。没有平台材料时列证据归档项，不重复提交或为只检查/规划任务强制登录 |
| 用户只说“通过了”“好了”，无法区分审核通过与正式发布 | 先查已有可观察信息；仅当仍影响下一动作时问一个具体问题。用户已给出明确状态后不反复追问相同问题 |
| 当前平台显示审核中，用户却说已上线 | 先核对账号、应用、版本、地区、发布方式及两条信息的时间。若仍是同一对象的直接矛盾，保留冲突，只暂停依赖它的发布动作；不能机械认定“最新一句话”或“本地最新文件”永远正确 |
| 当前源码已是新版本，平台通过的是旧版本 | 分别记录开发、候选与线上状态；旧版本成功不能给新版本授予通过，也不能因新版本未测就抹去旧版本的发布结果 |
| 本轮重算哈希匹配历史测试包 | 可写“同一包的历史回归记录仍适用其原环境”；不能写“本轮重新测试通过”，也不能将模拟器覆盖扩展到其他 API、ABI 或设备 |
| 发布包与当前文件/哈希不一致 | 保留两者，查来源及提交关联；只将该包依赖的测试或发布对应关系列为待核对，不覆盖历史证据或假定当前包就是线上包 |
| 旧构建目录丢失，但包与发布证据仍在 | 保留已完成的构建/发布历史；安排构建可复现性恢复，是否立即重建由本轮终点决定。目录丢失本身不要求重打已上线版本 |
| 修复分支有发布提交，main 或锁文件仍旧 | 区分已发布功能与源码整合/维护欠项；明确建议的接续基线，不盲用 main 或旧默认依赖，也不自动合并、推送或改锁文件 |

没有找到证据只能说明本次范围内未找到，不能直接宣告功能未完成、材料没提交或行为不合规；同样，已上架不证明所有测试、授权资料和构建环境都齐全。

## 实际进展与证据完整度分别记

面向用户的当前快照应同时说明“项目做到哪一步”和“这个结论凭什么”。用户确认可以用于检查/规划接续，但不能冒充 agent 已查询平台或亲自复测。

若使用可选 JSON 台账，保持其证据规则：仅有用户口述时可保存 `manual` 记录，不能改标成 `portal` 来让 submission/review 通过。尚缺所需平台证据时保留 pending，并在 `reason` 指向当前快照，注明“用户确认已完成，待补独立证据；禁止据此重复操作”。已有有效 portal 证据则保留，不为套新模板清空阶段。缺少文件导致 helper 失败也只是证据完整性失败，不等于历史操作失败。

`next_gate` 不能解决版本、时效或语义冲突，不据它自动重建、上传或提交。已有工程只需文档计划时，不强制新建 JSON，也不为了全绿要求登录或重新跑完所有测试。

## 从快照形成接续计划

将遗留项分为以下几类，并明确它是否影响**本轮终点**：

- **当前必做**：真实缺陷或缺少必要前置条件，影响当前交付；写清依赖和解除条件。
- **证据待补/归档**：可能已完成，但版本关联、回执、材料或测试记录不足；下一步是查证或整理，不默认重做操作。
- **维护欠项**：分支未合入、临时构建目录丢失、工具链文档过时等；安排恢复与审核，不能误报为应用尚未发布。
- **后续改进/未覆盖范围**：未测环境、额外机型或计划外功能；按风险及后续版本范围安排，不凭空升级成官方强制条件。

沿用现有工作记录，在入口增加有日期的当前摘要和下一动作；历史段标明适用时间/版本，保留原始结果。只修订会误导接续的入口和结论，不重写所有历史文档。需要用户操作才使用 [交接机制](handoffs.md)；不为将来可能用到的登录、权限、设备制造当前阻塞。

交付应让下一位执行者能回答：接着哪个工作副本/候选做、哪些旧结论已被新信息替代、哪些证据仍有效、下一步为什么需要做。若已达用户原目标，转为说明现状与范围内收尾，不擅自重新发布；若目标是新版本，另建候选与验证链。
