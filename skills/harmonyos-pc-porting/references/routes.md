# 按项目确定移植路线

## 先拆结构，再做选型

把 UI、业务核心、运行时、后台服务、平台接口、第三方依赖和资源分开画清楚。逐个列出文件/目录证据及依赖，不把“主要用某语言”当作完整画像。相同语言的程序可能分别依赖浏览器 DOM、桌面 GUI、驱动或命令行工具，移植工作会完全不同。

平台耦合表至少覆盖项目实际用到的窗口/渲染、键盘鼠标/IME、文件与持久化、网络、进程/线程、动态库、设备驱动、通知/剪贴板和认证。依赖记录区分宿主构建工具与随应用分发的运行依赖；传递依赖要从构建和实际包内容继续核对。

## 环境预检与原项目基线

使用项目实际需要的工具入口，检查 DevEco/SDK、Hvigor/ohpm、目标编译器及 hdc 或项目等价工具的路径和版本；能否读取源码、锁定依赖及获取所需目标库。不要只检查目录存在。模拟器需确认镜像类型、API、ABI 与应用相容，并确认实际启动可被调试工具发现。

先阅读已有原平台的构建和测试记录；可行且在任务范围内时运行代表性的基线流程，记录原行为、样例数据与输出。无法运行上游时，明确哪些预期来自文档/源码，避免移植后连原本功能是什么都无法比较。工具安装、私有源访问或系统授权卡住时，按 [交接与恢复](handoffs.md) 请求必要操作。

## 路线选择参考

| 原架构 | 可以考虑的路线 | 先验证什么 | 不要直接假设什么 |
|---|---|---|---|
| Electron + Web UI | 复用 Web UI，评估 ArkWeb + 原生桥；或使用经核验的兼容方案 | 渲染、路由、桌面 API 桥、关键业务闭环、文件交互 | Electron 主进程、Node API、原生插件在 ArkWeb 内天然可用 |
| 原生 C/C++ 业务 + GTK/Qt | 保留核心与已支持的 UI 后端；或重新实现 UI | 工具包目标后端、最小窗口、绘制、输入、缩放与销毁重建 | NDK 可编译 C 就等于 GTK/Qt 完整受支持；Linux `.so` 可直接用 |
| C/C++ 自绘界面、SDL 等多媒体应用 | 评估可用后端，或保留绘制/计算核心并适配窗口、输入、音频和文件接口 | 实际应用中的帧提交、坐标映射、事件顺序、音频回调及资源释放 | 核心已产出像素/PCM 就等于目标窗口已显示、实际音频已输出 |
| Python + 本地 Web / 桌面 UI | 评估嵌入运行时、目标扩展包、桥接和界面路线 | 关键依赖导入与真实计算、运行时初始化、资源加载、应用沙箱内运行 | 主机 Python 成功、纯 Python 声明或 shell 测试足以证明包内运行 |
| CLI / 计算库 | 目标交叉编译 + 适合应用模型的 UI/接口包装 | 最小实际计算、I/O、线程/子进程、错误和取消 | 原来的子进程、任意路径或终端调用在应用内具有相同权限 |
| Java/.NET/Rust/Flutter/其他 | 先核对目标 SDK/框架支持、已有适配、FFI 或替代实现成本 | 对应运行时/框架最小目标应用与最关键依赖 | 可在 Android/Linux/macOS 运行就能在 HarmonyOS PC 运行 |
| 多进程、网络服务或混合架构 | 分组件决策，再验证通信与生命周期 | 谁启动/停止、后台限制、端口/权限、重启、离线行为 | 可随意把本地能力移到云端；这会改变用户体验和数据流 |

选择表是候选，不是官方支持列表。新技术栈需要补充依据与原型。保留上游 UI、部分重写、完整重写与功能裁剪的成本不同，功能减少或云化应先向用户讲清影响。

## 最小原型决定路线能否继续

选择一个最可能使整个方案失败的真实任务。写明目标环境、输入、预期结果和通过条件，并保留执行结果。例如：

- Web 路线：真实页面调用一个关键系统接口，处理取消和失败，再运行一次核心业务。
- GTK 路线：真实 GTK 控件显示、键入文本、缩放、关闭重开；只有 XComponent 背景显示不够。
- 自绘/多媒体路线：在实际应用进程贯通“核心输出 → 平台呈现/播放 → 输入回到核心”；黑屏或无声时分开检查数据生成、缓冲格式/生命周期、提交与呈现，不能用独立 CLI 探针代替整包闭环。
- 解释器路线：从最终应用载荷导入最难的原生扩展，执行实际运算并显示/保存结果；只验证 `import` 的结论限于导入。

若无目标设备，先做可用环境上的原型并标明证据级别。项目计划给原型明确的检查点；失败后比较补齐后端、替换依赖、调整 UI 或变更范围的成本，不把备选方案写成必然可在原工期完成。

## 构建与适配的共同工作

- 固定上游基线、补丁和依赖来源，记录编译器/SDK/API/ABI。工具链文件名、路径和受支持 ABI 以当前 SDK 为准，不复制其他工程的绝对路径。
- 原生库核对格式、架构、导出符号、动态依赖闭包与包内布局；避免把宿主库或链接 stub 当作可运行载荷。
- 解释器及扩展根据实际目标 ABI 与版本挑选/构建。库版本、包索引和签名处理需要针对当前目标核对。
- 配置、用户数据、缓存和只读资源分开；以应用身份验证权限。优先从对应系统能力设计导入导出，而不是照搬桌面绝对路径。
- 桥接定义生命周期、线程归属、异步完成/错误、取消、编码与所有权。事件或输入重复、过期回调和阻塞调用用最小复现处理。
- 接手已有工程时核对正在打开/构建的是哪个工作副本；补丁、缓存库和包之间建立对应关系。合并源码后重新验证受影响产物。

具体修复使用当前源码和错误证据，应用补丁、重签、删除依赖或关闭功能前，先确认其必要性与适用条件。
