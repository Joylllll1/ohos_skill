# 验证与阶段证据

## 区分证据能说明什么

| 证据 | 可以支持 | 不能单独支持 |
|---|---|---|
| 主机单元测试 / 静态检查 | 算法或接口在所测条件下正确 | HarmonyOS 应用可运行 |
| 交叉编译 / ELF 和包结构检查 | 能生成目标格式、布局与依赖检查结果 | 库能在应用进程加载、UI 可操作 |
| 目标 shell / CLI 探针 | 该身份与环境的原生能力 | 同一操作在应用沙箱具备相同权限 |
| 模拟器交互 | 指定 OS/API/ABI 的模拟器场景 | 所有真机、驱动、窗口/输入环境一致 |
| 本地或云真机交互 | 指定设备和候选包上的已测场景 | 其他设备/系统或未测功能通过 |
| 发布签名检查 / 上传成功 | 签名工具或平台接受该产物 | 审核通过、功能全部正确、已上线 |

报告不要只写“测试通过”。绑定源码提交/未提交改动、生成时间、包哈希、versionCode、系统/API/ABI、设备种类、步骤和结果。构建 API、兼容 API 与实际运行 API 分别记录。

## 按真实功能选择测试

以用户任务为主，例如“新建→编辑→保存→冷启动重开”。UI 能显示不代表业务数据真实；使用实际生成的数据验证持久化，避免测试夹具或旧成功标记污染结论。

可参考 [Klavaro 的鸿蒙 PC 验收案例](klavaro-hap-validation.md)，了解 C/GTK 项目如何核对测试 HAP、验证成绩冷启动读回并交接输入问题。

HarmonyOS PC 桌面交互按功能选择：

- 窗口调整、最大化/恢复、不同缩放/密度、最小可用尺寸；检查布局和实际点击坐标。
- 鼠标点击/拖动/滚轮、键盘快捷键、Tab 焦点、输入焦点恢复；涉及文本时验证 IME 预编辑/提交/取消和非 ASCII。
- 文件选择器确认、取消、不可访问目录、不支持/空/大文件；读写和导出后数据是否正确。
- 页面/窗口/会话关闭重开、前后台切换、重复操作，必要时并发或高频输入；处理迟到回调。
- 首次启动、正常升级及数据保留、离线/联网失败、错误提示及恢复；卸载测试可能删除用户数据，应使用测试环境并确认范围。
- 多语言项目区分 UI 翻译、输入法、语料内容和语言选择持久化，不用其中一项代替其他项。

不是所有应用都需要所有场景。标明适用性和理由，覆盖用户承诺的能力与高风险边界；不要为了填满表格凭空添加业务要求。

## 改动如何使证据失效

从源码/补丁 → 原生库/前端资源 → HAP → 发布 APP → 截图/说明记录来源关系。修改业务库后旧包的功能结果不能证明新包通过；名称/图标更改后旧截图和隐私声明也需核对。重签/重新组包后确认业务载荷是否一致，必要时重测受影响范围。

发现变更后，先将受影响的当前阶段从 pass 改为 pending（有明确前置阻塞则 blocked），记录原因，再选择下一步。保留旧证据和提交回执作为旧候选的历史，不能通过重写哈希让旧结论看起来属于新包。纯材料修改通常只重开相应候选材料和提交/审核步骤；不强制重做不受影响的原生构建。新版本与正在审核的旧版本分别追踪，先查平台现状再决定操作。

审核整改首先记录审核员的版本、设备、系统、语言、复现步骤和视频/截图，使用相同条件回归。只能在另一个环境复现或验证时，明确差异，不用低版本模拟器覆盖高版本真机的结论。

## 阶段台账工具

`porting_helper.py init` 生成 JSON 台账；`check` 核对结构和证据完整性。证据根目录用于限制引用范围，建议用项目现有证据目录或专门交付目录。记录 `path` 使用相对根目录路径，`sha256` 为文件真实哈希，`environment` 为 `host`、`emulator`、`device`、`portal`、`manual` 之一。哈希可用 `shasum -a 256 <文件>` 获取。

记录约束：通过的阶段需要证据；目标环境阶段（保留 ID `device_validation`）接受 emulator 或 device 证据；提交/审核阶段需要 portal 证据。host 证据不能独立证明目标运行通过。模拟器可用于完成项目约定的运行验证；涉及真实外设或已知真机问题时，由 agent 根据测试计划判断补测范围，不将模拟器结果扩展到未测设备。台账是人工维护的事实声明，环境标签与文档内容仍需核验，脚本无法证明它们真实或足够。

`check` 输出的 `evidence_integrity` 用于发现遗漏，不是发布合规判定；只有完整性检查通过时才提供下一未完成阶段，检查失败时先处理 issues。不要根据退出码自动提交或发布。

blocked 必须填写非空 reason，可指向交接记录；工具输出会保留该原因，但不验证其中描述的操作已完成。`next_gate` 是顺序上首个未完成阶段，不是唯一可做任务；也不检查阶段证据属于哪个候选、发布是否实际生效或是否达成用户终点。由 agent 对照项目计划的候选身份和发布检查点核验这些事实。
